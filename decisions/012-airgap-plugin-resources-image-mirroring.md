# ADR: Airgap Plugin Resources Image Mirroring

## Context

**Problem**: RHDH deployments in air-gapped environments cannot pull container images from external registries (quay.io, docker.io, registry.redhat.io).

**Scope**: This ADR addresses **plugin dependency container images only** (databases, sidecars, task runners). Plugin OCI artifact mirroring is **out of scope** - it is already solved via existing mechanisms (`pkg/model/dynamic-plugins-mirror.go`).

In disconnected clusters, plugins deploy runtime dependencies as container images. These dependencies vary per installation (based on enabled plugins and flavours), making them impossible to declare statically in the operator's CSV `relatedImages`.

**Who is impacted**:
- OpenShift users deploying in disconnected environments
- Kubernetes users in air-gapped networks

**Constraints**:
- OpenShift priority, then vanilla Kubernetes
- Must handle dynamic plugin dependencies
- Requires cluster-admin permissions and node access

## Decision

**Mirroring and resolving workflow:**

1. **Mirror operator + static images**
   - **OpenShift**:
     - Run `oc-mirror` with operator catalog → mirrors images and generates IDMS/ITMS YAML files
     - Apply generated IDMS/ITMS: `oc apply -f <generated-idms.yaml>` (requires cluster-admin)
   - **Kubernetes**: Use `skopeo` to manually mirror operator image (from operator release/registry) and static core images (from operator deployment manifests)

2. **Generate plugin dependency image list** from deployed operator
   - Read `plugin-resources.yaml` from operator ConfigMaps or container (see ADR-011)
   - Extract all `image:` references from manifests (manual or via script)
   - Manually add any hidden dependencies (CRs that create containers, indirect dependencies)
   - **For OpenShift**: Create `ImageSetConfiguration` YAML listing all plugin dependency images
   - **For Kubernetes**: Create two files:
     - Plain image list (text file with image URLs) for skopeo mirroring
     - `registries.conf` configuration defining mirror mappings

3. **Mirror plugin dependency images**
   - **OpenShift**:
     - Run `oc-mirror --config <ImageSetConfiguration>` → mirrors images and generates IDMS/ITMS YAML files
     - Apply generated IDMS/ITMS: `oc apply -f <generated-idms.yaml>` (requires cluster-admin)
   - **Kubernetes**:
     - Run `skopeo copy` for each image in the plain image list
     - Manually apply `registries.conf` to `/etc/containers/registries.conf` (or `/etc/containers/registries.conf.d/`) on each cluster node (requires cluster-admin/node access)

4. **Image resolution (redirecting pulls to mirrors)**
   - **OpenShift (CRI-O)**: Uses IDMS/ITMS (ImageDigestMirrorSet/ImageTagMirrorSet) auto-generated by `oc-mirror` in steps 1 and 3. Runtime-level redirection via CRI-O configuration.
   - **Kubernetes (containerd/CRI-O)**: Uses `registries.conf` applied manually in step 3. Runtime-level redirection via container runtime configuration.

## Alternatives Considered

### Alternative 1: DaemonSet for Kubernetes Resolving
- **Approach**: Deploy privileged DaemonSet to automatically write `/etc/containers/registries.conf.d/` on each node and watch ConfigMap for updates
- **Deferred for future consideration because**: Adds implementation complexity. Manual registries.conf modification is sufficient for initial support. Can be reconsidered in a future ADR if automation is needed.

### Alternative 2: Template-Based Rewriting
- **Approach**: Extend operator's Go template system with `{{ ImageMirror "image" }}` function in ConfigMaps
- **Rejected because**: Only catches operator-created resources. Misses user-provided CRs, Tekton tasks, plugin-created resources. Incomplete coverage for dynamic environment.

### Alternative 3: MutatingWebhook Approach
- **Approach**: MutatingAdmissionWebhook intercepts pod creation at API level and rewrites image references. Could work on HyperShift with hosted-cluster-admin permissions.
- **Deferred for future consideration because**: Not reliable enough for production use. Adds API overhead, requires certificate management, misses pods created before webhook deployment, and introduces race conditions. Runtime-level solutions are significantly more reliable. HyperShift air-gap support can be reconsidered in a future ADR if there is proven demand and webhook reliability concerns are addressed.

### Alternative 4: Static relatedImages
- **Approach**: Pre-declare all possible plugin dependencies in operator CSV
- **Rejected because**: Plugin dependencies are dynamic and installation-specific. Would require listing every possible database, cache, and sidecar image (100+ images), most unused in any given deployment.

## Consequences

### Positive
- ✅ Reuses standard OpenShift tooling (oc-mirror, IDMS/ITMS) - no RHDH-specific implementation
- ✅ Runtime-level redirection for maximum reliability
- ✅ Consistent configuration format across both platforms

### Negative
- ❌ Requires cluster-admin and node access on both platforms
- ❌ Manual registries.conf modification on Kubernetes (no automation in this ADR)
- ❌ Three-step mirroring process requires coordination
- ❌ No HyperShift support in this ADR

### Neutral
- ⚖️ Helper script for dependency discovery can be automated but manual extraction also works
- ⚖️ Further automation for Kubernetes resolving (DaemonSet as an option) can be added in future ADR

## Notes

**Out of scope - Plugin OCI artifacts**: This ADR only covers plugin dependency container images. Plugin OCI artifact mirroring (the `oci://` packaged plugins themselves) is already solved via existing mechanisms and is not addressed here.

**Out of scope - HyperShift**: HyperShift hosted cluster deployments are not supported in this ADR. MutatingWebhook approach was considered but deferred due to reliability concerns. Can be reconsidered in a future ADR if there is proven customer demand.

**Out of scope - Kubernetes automation**: Manual registries.conf modification is specified for Kubernetes. Further automation (DaemonSet as an option) can be added in a future ADR if needed.
